## Milestone 2 — Library & scan
- [x] **Prune deleted files**: successful scans remove items the scan neither saved nor found unchanged (the scan collects the set; `PruneExcept`), cascading to subtitles/play state. It was an `updated_at` cutoff until scans became incremental — touching unchanged items to survive the cutoff would have made every polling client refetch them.
- [x] **Incremental scans** (migration 0024): a file whose size and mtime match its stored item is skipped — no probe, no provider lookup, no write — so a rescan of an unchanged library is a directory walk and one query. Changed files rematch their series and season too. Series still on air are re-looked-up once per scan anyway, since their next episode date moves with no file changing. "Full rescan" in the admin, `?full=true` on the API and `cineva scan --full` redo everything. The first scan after the migration is necessarily a full one, as no mtimes are recorded yet.
- [x] Sidecar edits count as changes: the scan's own directory walk records an `.nfo`, local artwork or `.srt`/`.vtt` beside a film (subtitles only beside an episode), stored as a fingerprint in `items.sidecar_stamp` (migration 0032); adding, editing or removing one rereads the video.
- [ ] Music sidecars (`cover.jpg`/`folder.jpg`) are not part of the change test; a replaced album cover waits for a full rescan.
- [x] Unmatched films and series are retried after every scan on a backoff (1, 2, 4 … 32 days; migration 0033), at most 50 provider lookups per scan, with one info line when something matches. Lookups only — no file reads.
- [ ] The unmatched retry keeps an existing overview, since it cannot tell an `.nfo` plot from a tag synopsis; recording where an overview came from would let the provider's replace a tag's.
- [x] Episode-level TMDB metadata: titles/overviews/stills via the season endpoint (tags and filenames still take precedence where present).
- [x] Season posters / overviews via the TMDB season endpoint.
- [x] The TV scanner probes in parallel batches too (it read one file at a time, which made a first scan of a 10k-episode library take most of a day). The music scanner still reads tags serially.
- [x] Worker pool for probing: files are inspected a batch at a time in parallel (`probeBatch`, capped at 8 workers — each holds an open file and an ffmpeg context, and parallel seeking past a point makes a spinning disk slower, not faster). The rest of the scan stays serial because provider lookups are rate limited and SQLite takes one writer. Measured 1.9-2.8x on real files; ordering, progress reporting and cancellation are unchanged, and tested for all three.
- [x] Scan cancellation: POST /scans/{id}/cancel + admin Cancel button; scans stop within one file.
- [x] Scheduled rescans: `libraries.scan_interval` (a duration, "0" to disable) rescans every library on a timer, skipping any already scanning rather than stacking scanners on the same rows. A timer rather than a filesystem watch, deliberately — a watch needs a descriptor per directory, misses anything changed while the server was down, and sees nothing on a network mount, which is where most media lives.
- [x] Embedded title tags no longer overwrite a good parsed title: scene releases stamp their release name (or just the group, "EVO") into the title tag. A tag is now taken only when it is the same title spelled better — `PreferTagTitle` in parse.go. Dry run over the real library: 209 of 1133 titles corrected.
- [x] Release year is the last year token in a name, not the first, so "Blade Runner 2049 2017 Remux-1080p" keeps its title; dotted names ("American.Siege") get spaces when they contain none.
- [x] **Rich metadata captured**: genres, rating + vote count, tagline, backdrop artwork and collection, from the provider's detail endpoint (migration 0013). A search hit carries only genre *ids* and no runtime, tagline or collection, so the best match is fetched in full — a second request per title, which is the price of storing anything beyond a poster and a synopsis.
- [x] **Genres are derived from the library**, not a fixed vocabulary: `item_genres` is its own table, so `GET /libraries/{id}/genres` is a GROUP BY over what the films actually carry, and `?genre=` narrows the grid on an index. A library of documentaries never offers an empty "Western" row.
- [x] **Cast and crew** (migration 0014). People are stored once in `people`, keyed on the provider id, and shared by every film they appear in — which is what makes "more with this actor" a join on `credits.person_id` rather than a search by name that would be slow and wrong wherever two people share one. Credits ride along on the detail request via `append_to_response=credits`, so they cost no extra call. Cast is capped at 20 by billing order and crew to the jobs a viewer looks for, ordered Director first — a large film carries 538 crew entries.
- [x] Detail page shows the cast as a responsive grid of headshots with characters (wrapping to as many rows as the width allows — 2 at desktop, 5 at phone, never a sideways scroll), crew grouped by role, and tapping a person opens a panel of everything else of theirs in the library.
- [ ] Headshots are downloaded per person at w185. With a few thousand distinct people that is tens of MB — small next to the 2.1 GB of embedded cover art, but worth watching.
- [x] The detail page carries the film's own artwork behind it — the wide backdrop where there is one, the poster blurred harder where there is not, masked to fade into `--bg` so it works in a light theme as well as a dark one.
- [x] Local `fanart`/`backdrop` images are picked up for any film, matched or not (see the NFO entry), so a library carrying its own artwork gets a backdrop without a provider match.
- [x] Person page: a filmography split into Acting and Crew, newest first, each credit showing the character or job. Several jobs on one film collapse into one row ("Director · Writer"); acting in a film you directed stays two rows, because that is two distinct facts. The summary line gives the jobs they are known for, the year span and the count, and is recomputed after library-grant filtering so it never describes films the viewer cannot see.
- [x] Collections surfaced: a Collections sub-tab on the library, `GET /libraries/:id/collections` (sets the library holds 2+ films from, largest first, with the earliest film's poster standing in) and `GET /libraries/:id/collections/:cid` (the films, in release order). Detection needs no franchise list of our own — TMDB's `belongs_to_collection` already groups Harry Potter, James Bond, The Lord of the Rings and the rest; a film only has to be matched.
- [x] Rating filter on the grid (Any / 6+ / 7+ / 8+). An unrated film is excluded by any minimum rather than treated as zero: "7+" means "known to be good", not "not known to be bad". `vote_count` remains tooltip-only, which is the right weight for it.
- [x] Multi-field search: `/search` matches title, display artist, release year (a bare four-digit query) and credited people, so "Scorsese", "1995" and "Goodfellas" all find the right films. Ranked rather than merely filtered — a title match outranks a person match, so searching a title does not bury it under everyone who worked on it. Alternative versions are excluded.
- [x] **Multi-version grouping**: movies matching on title and year are grouped, the best copy (highest resolution, then largest file) becomes the primary shown in the grid, and the detail page offers a picker over the rest. Re-derived from scratch on every scan after pruning, so it is idempotent and self-healing. Verified against the real library: 1187 movies, 30 grouped away, 1157 listed.
- [x] Watch state is shared across a film's versions: `Store.primaryID` resolves a version to its primary, and `SetProgress`/`SetWatched`/`PlayStateFor` all record and read against that, so resuming a 4K rip and switching to the 1080p one continues where it left off.
- [x] Version grouping keys on the TMDB id where both rows carry one, falling back to title+year for unmatched files — so two copies of a film group even when one filename lacks the year or spells the title differently.
- [x] **Extras/trailers are skipped**: the scan walk prunes whole `Extras/`, `Featurettes/`, `Behind The Scenes/`, `Trailers/` subtrees and ignores `-trailer`/`-sample`/`-featurette` suffixed files, matching the Plex/Jellyfin/Kodi conventions. They are skipped rather than catalogued — attaching them to the film as playable extras is a later step.
- [x] Cast/crew: `people` + `credits` tables (migration 0014), populated from TMDB `append_to_response=credits`. Embedded iTunMOVI plists in the mp4s remain an unused fallback for unmatched films.
- [x] NFO sidecar support (`<stem>.nfo` and `movie.nfo`, both `<tmdbid>` and `<uniqueid type="tmdb">`) plus local `poster/folder/cover` and `fanart/backdrop` images. Sidecar title/year/id drive the match; sidecar fields and local artwork are applied *after* the provider so the operator's own curation wins. A malformed sidecar is reported rather than silently ignored.
- [x] **Built-in TMDB key**: `metadata.defaultAPIKey` is injected at build time (`make build TMDB_KEY=...`) rather than committed, so the repository holds no credential. Precedence is `--tmdb-key` > `CINEVA_METADATA_TMDB_API_KEY` > config file > built-in, so a configured key is always a deliberate override. The TMDB attribution line is on the client Settings page, as their terms require. **The key itself still has to be registered** — a source build logs that metadata is unavailable and scans without it.
- [x] (Covered by the NFO entry above — this was the reason it was worth doing.)
- [x] Id-in-filename hints: `[tmdbid=12345]`, `{tmdb-12345}` and `[imdbid=tt...]` are read from the filename or its parent directory (`library.idHints`). A tmdb hint fetches that film directly instead of searching; a hint that fails to resolve logs and falls back to a search rather than silently becoming a wrong match.
- [x] Candidate ranking (`metadata.bestMatch`) replaces trusting TMDB's result order: titles are normalised (case, diacritics, punctuation, leading articles, "Thing, The") and scored against the parsed title, with an exact year worth more than an exact title and a wrong year penalised — which is the signature of the popular-namesake mismatch.

- [x] **TV series were being invented out of season folders and release names.** Three faults compounded:

  `scanTV` assumed the layout was exactly `Show/Season NN/file` and took the file's grandparent as the series. Anything nested one level deeper — a release folder per episode, `Season 03/Alone.S03E01.1080p.WEB-GROUP/` — made a *season* folder into a series of its own. `seriesDirFor` now finds the first directory beneath the library root whatever the depth, and `seasonDirFor` finds the nearest `Season N` ancestor rather than assuming the parent is one.

  `ParseEpisode` read the show name from the filename before falling back to the folder, so the scene name won: the library held series called `alone`, `Animal.Kingdom` and `Archer.2009`, none of which match anything at TMDB. The folder now wins wherever the layout identifies one, and the name goes through `showName`, which cleans dot-separated release names and lifts a trailing year out of `Archer (2009)`.

  `SearchTV` took no year, unlike `SearchMovie`. Series reuse titles far more than films do — "Alone" is a 2013 US series and a 2023 UK one — and the folder year was being discarded rather than used. It now takes a year and retries without it, so a folder named for a box-set release year degrades to the old behaviour instead of matching nothing.

  Verified by rescanning the real library: on a 177-folder, 10k-file TV library the old scan produced duplicate series pointing at season folders and two unmatched shows; the new one produces zero series whose path is a season folder, zero dotted titles, and zero unmatched series.

- [x] **A series had no way to start watching.** The detail page offered only "Download show" — a film gets Play, an album gets Listen, a series got nothing. `GET /items/{id}/next-up` now returns the episode to play for a series or season, with a reason — `resume` (part-watched, with the position), `next` (first never started) or `restart` (everything watched, so the first again) — so the button can say "Resume S02E05" rather than making a promise it might break. The decision is server-side, as CLAUDE.md requires, so the native clients cannot disagree with the web one about where someone is up to; it orders episodes by season then number, so it crosses season boundaries on its own. The page shows **Play/Resume S01E01** and **Play all**, which queues the series from that episode onward.

- [x] **176 episodes were being skipped outright.** The scanner required an `SxxEyy` marker in the filename and logged and dropped everything else, which on this library meant 176 files across ~30 shows — 47 of House of Cards, 15 of The IT Crowd, 12 of Peaky Blinders. The layout it refused is `Season 1/02 Part Two.mp4`: the season named by the folder, the episode by a number leading the filename, which is as common as the marker form.

  `parseNumberedEpisode` now reads that, but only from inside a season folder — without one a bare "02" says nothing about which season it belongs to, and assuming the first would merge a flat library into one. The number must lead the name and be followed by a separator, so "1917.mkv" is not episode 191 and "Season 1 - Outtakes" and "A Very Sunny Christmas" stay out rather than being given invented numbers and scattered through the season.

  Replaying the 176 paths the real scan refused: 152 now parse. The remaining 24 are bonus material in `Season N Extras` folders (which `extrasDirRe` now matches properly — it only caught a bare "Extras" before, so those files were being walked and refused one at a time, the right outcome by accident), six date-based Tonight Show episodes, and two named specials.

- [x] Date-stamped episodes ("Show - 2023-01-27 - guests") are matched by air date through TMDB's seasons; unmatched ones are placed as season = year, episode = month and day. Also fixed: in show folders without season folders, the season row took the show's path and overwrote the series.

- [x] **Series had no genres, no cast, no tagline and no age rating.** Two independent faults, either of which alone was enough to lose them. TMDB returns genre *ids* on a search hit and the real data only on the detail endpoint; `SearchMovie` has always followed its search with a detail call, `SearchTV` never did — so `TVByID` now mirrors it, with the television-specific fields (`content_ratings` rather than `release_dates`, `episode_run_time` rather than `runtime`) and `bestMatch` ranking instead of taking TMDB's first hit. And `scanTV` never called `saveGenres` or `saveCredits` at all, which the film scanner has always done, so anything fetched was dropped on the floor. 0 of 173 series had a genre against 1178 of 1187 films.

- [x] **The rest of what TMDB returns for television.** Migration 0022 adds `status`, `network`, `air_date`, `season_count` and `episode_count`. A series now carries its status in TMDB's own wording ("Ended", "Returning Series", "Canceled" — kept verbatim, because "Canceled" and "Ended" are not the same news), its broadcaster, how many seasons and episodes are supposed to exist, and its creator as a crew credit (TMDB keeps `created_by` outside `credits`). Seasons and episodes get their own `tmdb_id` at last, so either can be re-matched or refreshed on its own. Episodes get their broadcast date, rating and vote count.

  The air date matters most: it is the only date an episode has, and two thirds of the library had none, which also left nothing correct to sort by within a year. Verified against real TMDB data on one show — 25 of 25 episodes dated, status "Ended", network "Channel 4", 4 seasons / 24 episodes, creator Graham Linehan.

  The client shows status, broadcaster and "N of M seasons" on the series page, and the broadcast date on each episode row (hidden at phone width, where the title and runtime matter more).

- [x] **Specials were being thrown away.** `Specials/` was in the extras list, so 17 episodes across 6 shows never reached the scanner — every one properly marked `S00Exx`. Season 0 is where TMDB, Plex and Jellyfin all put Christmas episodes and one-offs; they are episodes people want. A file in there without a marker is still refused by the parser, so nothing bonus slips in by including the folder.

- [x] Episodes numbered straight inside the series folder — "Show/01_Pilot.mkv", no season folder — are now read as season 1 rather than refused. The marked form still wins where present.

- [x] A library pointed at a single show's folder produced a library of series called "Season 01", with no show at all and season lookups against an id that was never found. The root is now recognised as the series when its own children are season folders.

- [x] `TestItemRoundTripsEveryField` walked a hand-written list and went on passing when five columns were added — a test that cannot fail for the thing it exists to catch is worse than none, because it is believed. It now walks the struct by reflection, names any field the test itself left zero, and upserts twice with *different* values so the UPDATE branch is exercised too: the first version only ever inserted, and the update keeps an existing value when handed an empty one, so a column missing from the UPDATE would never have shown up.

- [x] **The last of the television metadata.** Migration 0023 adds `last_air_date`, `next_air_date`, `original_title` and `country`. `next_air_date` is the one with a shelf life — only a running series has one and it stops being true the moment that episode airs — so the update clears it as well as setting it, because a stale "next episode" date is worse than none. `original_title` is stored only when it differs from the title, or every English-language series would carry its own name twice. Episodes now get their `guest_stars` as episode-level cast, which is the only thing an episode cast is for: the regulars are already credited on the series.

  Verified against real TMDB data on *Alone*: status "Returning Series", network "History", country US, first aired 2015-06-18, last 2026-09-09, 13 seasons / 144 episodes. `next_air_date` was correctly empty (nothing scheduled) and `original_title` correctly empty (an English title).

- [ ] **The TV library needs one full rescan** — rows from the old scanner keep their parentage, and in show folders without season folders unchanged episodes stay under the formerly corrupted series row until reread. Queue it with "Full rescan tonight" on the admin Libraries page (runs in the background window with nothing playing); it also refreshes the ~3,200 episodes still carrying embedded posters.


## Milestone 3 — Playback
- [ ] **PGS/VobSub burn-in — blocked upstream, not by effort.** Everything on our side is written and tested: the compositor alpha-blends a palettised bitmap onto a scaled frame for both yuv420p and nv12 (`compositeBitmap`, with unit tests for the blend, the BT.601 conversion, out-of-range clipping and a real frame), the pipeline feeds and paints at the right points, and the API and player offer the tracks and restart as a re-encode when one is chosen. Two things in the vendored ffmpeg-statigo stop it running:
  1. **No way to allocate an `AVSubtitle`.** Every function takes a `*AVSubtitle` but nothing constructs one and the pointer field is unexported, so `AVCodecDecodeSubtitle2` cannot be called — passing a zero value segfaults the moment the decoder writes to it (confirmed).
  2. **No `pgssub` decoder in the build.** `dvdsub` (VobSub) is present; PGS, the Blu-ray format, is not — and it is the majority in practice (93 PGS vs 28 VobSub streams across a sample of this library).
  `newSubBurner` refuses up front with `ErrBurnInUnsupported` rather than crashing. Unblocking it is an upstream change: an AVSubtitle allocator, and `--enable-decoder=pgssub` in the ffmpeg build.
- [ ] **Portable-transcode download** (H.264/AAC MP4 variant): deferred to milestone 8's async-job infrastructure — the download button serves the original file today.
- [x] **Audio track picker**: the scanner catalogues audio streams (migration 0011) the way it does subtitles, the play response carries them with the chosen stream index, and the transcode session plays the requested one. Picking a track restarts the session like a quality change, since a session muxes one track.
- [x] **Playback info overlay**: a transparent panel over the picture behind an info button, showing the source (resolution, codec, HDR/Dolby Vision, container), what is being sent (direct / copied 1:1 / re-encoded at what height), the audio track and whether it is being converted, why a transcode was chosen, and buffer depth. Backed by a new `source` object on the play response.
- [x] The info overlay shows the transcode path (the device, or "on the CPU"), whether HDR is being tone mapped, and a live bitrate measured from the segments hls.js actually fetched — falling back to the file's own average on direct play, where there are no segments to measure.
- [x] Audio tracks are backfilled at play time when an item has none stored — the file is already open for the probe, so a library scanned before migration 0011 gets a working picker without anyone being told to rescan, and the row is saved so the next play takes the cheap path.
- [x] Playlist duration accuracy. The cause was not keyframe placement but rounding: the GOP is a whole number of frames, so at 23.976 fps a "six second" segment is really 144 frames = 6.006s, and writing 6.0 into every EXTINF lost 6ms a segment — **7.2 seconds across a two-hour film**, measured in a test. The playlist now states the true duration, and `gopFrames` is the single definition the encoder's keyframe interval and the playlist both derive from, so they cannot disagree. On a remux the boundaries land on the source's own keyframes, which we do not control, so it stays the best estimate available.
- [x] Seek-preview thumbnails: one sprite sheet and one WebVTT index per item, generated lazily in the background on first request and cached. A sheet rather than a file per thumbnail — 391 separate images would be 391 requests for one drag of the scrub bar. Measured on a 2h36m 4K source: 391 previews in 61s, a 618 KB sheet. The player shows the frame and timestamp on scrub-bar hover.
- [x] Transcode sessions survive a restart (migration 0019). The description is stored; the segments were always on disk and are now kept rather than deleted on shutdown, and the orphan sweep spares the directories a restored session owns. A restored session transcodes nothing until a segment is asked for, at which point the existing restart-at-offset path starts it where the viewer is. Verified: played, restarted the server, then served both an already-written segment from disk and one far ahead that required the transcoder to resume.
- [x] The look-ahead collapses once a session stops being requested: 120 seconds while someone is watching, 15 once nothing has asked for a segment in 20. A closed tab now stops costing CPU within seconds instead of transcoding two minutes ahead and then sitting idle until the janitor reaps it. A viewer who merely paused loses only buffer depth, which refills on the next request.
- [x] **Orphaned transcode directories are swept at startup and the cache is capped.** `media.SweepOrphans` runs before the first session (every directory present is by definition stale, since sessions die with the process), and the janitor enforces `transcode.max_bytes` / `CINEVA_TRANSCODE_MAX_BYTES` (default 8 GiB) by evicting least-recently-used session directories, never a live one. This mattered more than it looked: the default transcode directory is under `/tmp`, which on a systemd host is tmpfs — i.e. RAM — and 6.9 GB had accumulated on this machine.
- [x] Default quality and next-episode autoplay are per-user on the server, via the same `user_prefs` store.
- [x] **Play queue**: playing a collection loads the whole set into a queue from the server's next-up and rolls through it; a single film replaces the queue with just itself, so "play this and stop" stays the default. Queued films can be removed or jumped to, "Add to queue" appends from a film's page, and the queue honours a collection's managed order.
- [x] **Collection progress and next-up**: each collection reports how many of its films the viewer has finished and which one is next, in the collection's own order, decided server-side (`LibraryCollections`) so native clients behave identically. Shown as a progress bar and count on the tile, and a Continue/Play button on the collection page.

- [x] **Playback freeze on 4K HEVC**: auto-transcode chose a remux (video copy) even when the reason for transcoding was the video codec, handing the browser the same stream it had just said it could not decode. Video is now re-encoded whenever the codec is unsupported *or* cannot survive a copy into fMP4 (only h264 can — HEVC needs the hvc1 sample entry, carries Dolby Vision configuration browsers will not render, and `canPlayType` reports hvc1 playable whenever the GPU can decode it, which is not the same thing).
- [x] **Transcode was ~1x realtime and stalled**: the vendored `av.NewDecoder` opens its codec without setting thread_count, so 4K HEVC decoded on one thread (1.3x vs 7.1x with all cores). `internal/media.threadedDecoder` sets it before open; with an explicit x264 `veryfast` preset the 4K pipeline went 0.9x -> 3.6x realtime.
- [x] **Abandoned direct-play streams**: switching titles left the previous `<video>`'s range request open (one held a connection ~55 s and 100 MB), which with SSE and admin polling exhausted the browser's six-per-origin limit and stalled the next title's segments. The player now aborts the media load on teardown.
- [x] **HEVC is remuxed, not re-encoded**, when the client can decode it: video reaches the browser bit-for-bit at full resolution for ~0% CPU, and only the container and audio are changed. Gated on the Dolby Vision profile, read from AV_PKT_DATA_DOVI_CONF at play time (profile 8 / base-layer compatibility 1 is HDR10 underneath and copies fine; profile 5's IPT base layer is false colour without a DV pipeline, so it is re-encoded). The HLS muxer writes an `hev1` sample entry regardless of codec_tag, which browsers dislike, so `forceHVC1` corrects it in the served init segment alongside `stripEdts`.
- [x] HDR re-encodes tone map to SDR BT.709 (`media.videoFilterSpec`): zscale to linear light, hable tone curve with `desat=0`, back to BT.709, scaling last so the curve is applied at full resolution. Covers PQ and HLG. Verified against the 4K PQ sample — a no-op control scores exactly 0 mean absolute per-pixel difference, the chain scores ~4/255, and reference ffmpeg running the identical chain reports 28-30 dB PSNR between the two pipelines.
- [x] `quality=original` now means "keep the video bit-for-bit, change only what must": it direct plays when the device can take the file, otherwise remuxes (video copied, container and audio fixed), and only re-encodes when the stream cannot survive a copy into fMP4. Previously it returned a direct-play URL that could not play an mkv.
- [x] libva is `dlopen`ed, not linked: the host's libva is required (a VA driver is version-locked to it) but a hard `DT_NEEDED` entry stopped the binary starting at all where it is absent — fatal on headless and slim-container hosts, which are the main deployment targets. `internal/media/libva_shim.c` defines the 48 entry points ffmpeg references and forwards them to a `dlopen`ed libva. Safe because every one takes only pointer/integer-class arguments (no float, double or by-value struct), so a uniform 12-argument forwarder — above the maximum real arity of 11 — matches the SysV x86-64 ABI for all of them. Verified in a sandbox with no libva on the filesystem: server starts, reports "libva is not installed on this host", falls back to software, no crash.
- [x] Shim coverage is checked by a test that diffs `nm -u` on the vendored archive against the forwarders in `libva_shim.c` (48 for 48). Worth noting what it does and does not add: a *missing* forwarder already fails the link, verified by removing one — the shim is what satisfies ffmpeg's undefined references. What the test contributes is the readable form of that invariant, plus the reverse case nothing else catches: forwarders kept for symbols no longer referenced.
- [x] **Hardware encode**: frames are scaled on the CPU to NV12, uploaded into a device frame pool (`AVHWFrameCtxAlloc`/`Init`, surface format per backend, sw_format NV12) and encoded by the vendor encoder (`h264_vaapi` and friends). Falls back to software if the pool cannot be built, and `Session.Accel` reports the path actually taken via `HLSJob.OnAccel` rather than the one intended. Measured on a 1080p h264 source: 30.9s CPU for 60s of video on libx264 veryfast vs **3.6s on h264_vaapi — 8.6x less CPU**.
- [x] Hardware encoders emit packets with no duration, so the HLS muxer guessed segment boundaries ("packet with pts N has duration 0"). One frame of the output timebase is now filled in from the stream frame rate; EXTINF entries came back as exactly 6.000000s.
- [x] **Hardware decode**: both routes are wired, and on a build with VAAPI hwaccels compiled in it engages and is measured.
  - *Standalone hardware decoders* (`hevc_qsv`, `hevc_cuvid`, …) — found by name, device attached, frames emitted as device surfaces. This build has 18 of them, so **QSV and NVIDIA hosts get hardware decode**.
  - *hwaccel* (software decoder + `hw_device_ctx` + a `get_format` that picks the device surface) — VAAPI's only route.
  - Scaling happens on the CPU after a download (`downloadFrame`, `AVHWFrameTransferData`), not on the GPU. A device filter graph is impossible with this binding: the `buffer` filter rejects a hardware pix_fmt at parse time, and `avfilter_link`/`avfilter_inout_alloc` are unbound, so a graph cannot be assembled by hand either. `hwfilter.go` was deleted and `swgraph.go` took its place.
  - The download loses everything but the pixels, so `downloadFrame` restores the timestamps *and* the colour properties — zimg refuses a frame that declares no transfer function or primaries. `newParsedGraph` likewise declares `colorspace` and `range` on its `buffer` source: a filter link carries them, and an undeclared link fails HDR tone mapping with "no path between colorspaces" rather than guessing.

  **Measured on this host** (RX-class VAAPI, 4K HEVC source, 24s of 1080p output, against a locally rebuilt library with `hevc_vaapi` and friends enabled):
  - SDR: **73% less CPU** (1m7s → 19.7s). `TestHardwareDecodeCPUCost`.
  - HDR with tone mapping: **39% less CPU** (44.3s → 26.9s). `TestHardwareDecodeCPUCostHDR`. This was 9% when measured, because tone mapping at 4K dominated everything; moving the downscale ahead of it cut the whole job from 1m39s to 44s and left decode as a much larger share of what remains.
  - Wall-clock is slightly *worse* on the GPU path (the download adds a round trip per frame). CPU headroom is what matters for concurrent streams, so this is the right trade, but it is not a latency win.

  **Not shipping yet:** upstream ffmpeg-statigo builds with no hwaccels (`Total hwaccels: 0`), so a stock install still cannot VAAPI-decode however the code is written. The measurements above come from a local rebuild. Enabling them upstream is a feature request, not a bug fix — their codec matrix lists VA-API as encode-only deliberately.

- [x] Hardware decode no longer requires hardware encode: a GPU that decodes but cannot encode feeds libx264, and a hardware encoder that will not open falls back to libx264 instead of failing playback. Safe only because frames are now scaled on the GPU (`scale_vaapi`, at the source's bit depth) before being copied back — copying full 4K frames made GPU decode plus libx264 slower than all-CPU. Measured on the Radeon 780M here: through the hardware encoder SDR went 3.25x to 7.0x realtime (CPU 20.6 s to 4.5 s) and HDR 2.14x to 2.87x; through libx264, 4.17x against 3.07x all-CPU. Picture within 0.3/255 of the old path. VAAPI only; `scale_qsv`/`scale_cuda` need the same checking.
- [x] The GPU-decode list comes from the driver's own decode profiles (asked through the libva shim), not from what the build contains; the startup log names what stays on the CPU (`on_cpu=mpeg2` on this machine).
- [x] **Hardware encodes were starved of bitrate.** The encoder had no frame rate, so VAAPI rate control took 1/time_base (1000 fps for Matroska) and wrote 0.32 Mbit/s against a 6 Mbit/s target, so every hardware transcode looked soft and blocky; from a source with a 1/16000 time base (Succession S03) h264_vaapi never returned from its first frame and playback never started. The frame rate is now set on hardware encoders (6.19 Mbit/s; that episode transcodes at 19x realtime) and `TestDeviceEncodeCost` checks the bitrate.
- [ ] Earlier hardware-encode measurements in this section (3.25x to 7.0x realtime, 20.6 s to 4.5 s of CPU, and the HDR figures beside them) were taken while the encoder wrote about 0.3 Mbit/s, so they overstate the gain; re-measure.
- [x] Frames stay on the GPU from decode to encode when nothing needs them in system memory (hardware encoder, 8-bit source, no burn-in, no tone map): `scale_vaapi` feeds h264_vaapi directly (`videoGraph` in `devicescale.go`). Measured on an 8-bit H.264 episode against the copy-back path, bit-identical after the encoder: 1080p to 720p 19.7x to 23.6x realtime with 46% less CPU; 1080p to 1080p 13.5x to 16.6x with 63% less. Anything else, or a graph that will not build, takes the copy-back path.
- [ ] Frames kept on the GPU for 10-bit sources: needs the device's P010 to NV12 conversion matched to swscale (currently 0.05-0.27 levels darker), or an encoder that takes P010.
- [ ] Keeping frames on the GPU is verified on AMD radeonsi only; check on Intel iHD and add `scale_qsv`/`scale_cuda` equivalents. A transcode failure is not retried by the session, so an unverified driver failing here would fail the playback.
- [ ] libx264 is not given the frame rate. Setting it moved its bitrate (5.2 to 6.5 Mbit/s against a 6 Mbit/s target on an SDR episode); weigh it on its own.
- [x] All-CPU re-encodes were 1.7 (8-bit SDR) to 2.5 (10-bit) luma levels darker than reference ffmpeg: the vendored helper's buffer source declared no colour space or range, so swscale converted colour it did not need to. The software decode now uses the same first-frame graph as the hardware path; bit-exact with reference ffmpeg (`TestCPUGraphMatchesReference`), and the filter stage uses 20-58% less CPU.
- [x] AV1 decodes on the GPU: decoders are chosen by what the device supports, so AV1 uses the native `av1` decoder with VA-API and libdav1d on the CPU (bit-exact against libdav1d). A hardware decoder that fails before its first frame hands over to software and replays its packets.
- [x] **HDR playback stalled because the transcode could not sustain realtime.** Measured on a 4K HDR source: 0.88x realtime to 1080p and 0.78x to 720p, against 2.79x for the same file treated as SDR. Under 1.0 the buffer drains and the player pauses however much CPU is spare — which is what "it randomly hangs" was. Not random, and only on HDR.

  The cause was the filter order. Tone mapping runs on every pixel through a float conversion, and the chain put the downscale *last* so all of it happened at 4K — four times the pixels for the same result. Scaling first takes it to 1.61x, and 720p now costs less than 1080p as it should.

  The picture is the same to **0.28/255 mean luma difference**, against about 5/255 for the tone map itself, so the original worry about averaging already-mapped values costs nothing visible. The input colour properties are now stated outright (`min=bt2020nc:pin=bt2020:rin=tv`) because swscale does not carry HDR metadata through: without them zimg is handed a frame it cannot classify and refuses it. The first attempt at this change did exactly that while appearing to be the fastest of the three, because it was doing less.

  `TestTranscodeKeepsUpWithRealtime` now fails below 1.2x, a failure no other test in the package could catch: the output is correct, there is simply not enough of it.

- [ ] HDR tone mapping on the GPU. No longer blocked by the binding (GPU frames can feed a filter graph, and `tonemap_vaapi` is in the build) but by drivers: Mesa radeonsi refuses it ("VAAPI driver doesn't support HDR"). Intel iHD supports it — enable once an Intel host can check the output against `TestToneMapChangesPicture`. `tonemap_opencl` would need `--enable-opencl` in the patch plus libOpenCL loaded at runtime through a shim like libva's.

- [x] Hardware encode beyond h264: each backend's hevc and av1 encoders are probed at detection and reported (`HWContext.Alt`, `EncoderFor`, `Codecs`), shown in settings and named at startup — on this machine, "using h264_vaapi (device also encodes hevc, av1)". h264 remains the output deliberately: it is the one codec every browser decodes, and these exist for clients that can do better rather than to be chosen automatically.

- [x] `trickplay.vtt` now answers 202 while the sprite sheet is generating, instead of 404. The request was understood and the work is under way, so 404 was untrue, and it put a failed request in every viewer's console and in the server log for ordinary first-play behaviour. The player skips 202 explicitly and picks the cues up on the next load.

- [x] **Transcode sessions reported "Failed to open segment 'init.mp4'".** Stopping a session cancelled the transcoder and then slept a flat 200 ms before deleting its directory — longer than ffmpeg needs to shut down, shorter than it needs to start. A session superseded moments after it began had its directory removed while ffmpeg was still opening `init.mp4`. Media on a network share made that the common case rather than a rare one. It now waits for the transcode goroutine to actually exit, bounded at 5 s so a wedged transcoder cannot hold up a shutdown.

## Intro detection (pulled forward from "Later")
- [x] **Detection no longer competes with playback.** It used to read four files at once with no speed cap, restart after every scan (every 15 minutes), and check the share only at the start of a run; when reads stalled it moved on to the next file, stacking stuck reads on the one SMB connection the kernel shares between all mounts from a server, which hung every share on the host. Now: an admin chooses when it runs (Settings: only between set times — 02:00 to 06:00 by default — whenever nothing is playing, or only when started with "Analyse now" on the Activity page); reads default to one file at a time at up to 10 MB/s; and the first stalled read, or the library's share going down, ends the run without trying another file or saving anything for that season.
- [x] **Skip intro for TV.** Each episode's opening (the first quarter, at most 15 minutes) is decoded to 11 kHz mono and fingerprinted with the Philips scheme — 32-bit hashes of band-energy changes, ten a second (`media.FingerprintFile`, written in Go because our ffmpeg build has no Chromaprint). Each episode is compared at every alignment with up to four neighbours; the longest shared run of 15-120 s is a candidate, and the candidate most others agree with wins, with median boundaries (`internal/segments`). Stored in `media_segments` (migration 0025), served in the play info, shown as "Skip intro" in the player. Runs in the background after every completed TV scan and at startup, analysing only episodes whose current file has not been (`segment_analysis`); progress on the admin's Activity page. `libraries.intro_detection` turns it off.
  Verified on real files: Succession seasons 1-4, 39 of 39 episodes, every one the ~90 s title sequence wherever its cold open put it (as late as 10:44 in the S2 premiere, which is why the window is 15 minutes not 10); Doctor Foster S1, 5 of 5, its 59 s titles. About 1.6 s per episode to fingerprint from local disk, 5.6 s from the NAS; a comparison is ~140 ms.
- [x] **Credits detection** by the same comparison on each episode's closing stretch (the last quarter, at most ten minutes; 15 s to 6 min long). Detected credits move the up-next card to their start and autoplay counts down 15 s from there instead of waiting for the end of the file; reaching them also marks the episode watched, so skipping the credits cannot leave next-up pointing back at it. A credits match needs two comparisons to agree (an intro needs one): a false match there skips the end of the story, and on Succession single comparisons found "credits" six minutes before the end of the finale. Verified: Doctor Foster S1, 4 of 5 (the last 30 s; the finale's music differs); Succession S2 and Alone S5, none — their end music changes per episode or sits under a promo, and they keep the 40 s window.
- [ ] Visual credits detection — dark frames carrying text — for the shows above, which audio cannot reach. Plex combines both.
- [x] A season's lone episode is compared across seasons: it borrows up to four partners from the nearest seasons (the later season's opening episodes and the earlier season's closing ones, never specials), used only as comparison material. Verified on a lone Succession S2 episode: intro at 194-285 s. A series with a single episode in all is left unrecorded and tried again once it has company.
- [x] **Intro and credits by hand** (migration 0034): "Intro & credits..." in an episode's menu (admins) shows what detection found, takes start and end times or "No intro"/"No credits", and locks the result so detection and file changes leave it alone; "Back to detection" removes the lock. "Re-detect season" reopens every unlocked analysis and starts detection at once (still giving way to playback, scans and a pause); old times are served until replaced. `GET`/`PUT`/`DELETE /items/{id}/segments[/{kind}]`, `POST /items/{id}/segments/redetect`.
- [ ] A lone episode compared across seasons that found no intro is not looked at again when its season gains episodes; "Re-detect season" covers it.
- [ ] Hand-set times stay locked when the file is replaced, so an upgrade to a different cut may need them corrected.
- [ ] Fingerprinting read about 100 s per file from local disk during the polish work (15-minute windows), against the 1.6 s measured earlier; find out whether that was load from parallel work or a regression.
- [x] Within a season, files are fingerprinted and episodes compared in parallel (up to four at once, half the cores at most), results saved serially. Progress is reported live: the admin's Activity page shows episodes done of total, the current series/season and phase, elapsed and estimated time left, unreadable files, the latest outcomes with their intro times, and a summary of the last run.
- [x] **Detection gives way.** Its first pass read a quarter of every episode at ~117 MB/s — a gigabit link to the NAS, flat out — starving playback and anything else on the share. It now pauses before each file while anything is playing or a scan runs, and carries on a minute after they stop; an admin can Pause/Resume it from the Activity page (kept across restarts); and Settings has a read-speed cap (unlimited, 50, 25 or 10 MB/s — with a cap it reads one file at a time and paces itself to average under it).

And the queue survives a reload: it is kept in localStorage rather than on the server, for the same reason volume is (see `prefs.ts`) — a queue is what you have lined up on the device in front of you, not a property of the account. Items are stored whole rather than as ids, because restoring from ids needs either a request per entry or a wait for the library list, and a queue that is briefly empty after a reload looks exactly like one that was lost.

- [x] **Queue handoff between devices.** Each device keeps its queue on its session, so another can **Continue from…** it (the Queue page lists other devices' queues and what they are on); and **Play on…** sends this device's queue to another that has the app open, which starts it — a "handoff" event addressed to that session alone. Positions need not travel: resume points are per user and item already. Items the receiving user may not see are dropped on the way.
- [x] "Play on..." from the player: a cast button lists the user's other online devices; picking one pauses, saves the exact position, sends what is playing plus what is queued after it, and closes the player (it resumes if the send fails). At phone width the control row wraps and the volume slider gives way to mute.
- [ ] A receiving browser that blocks autoplay with sound shows a handed-over queue paused rather than playing.
- [x] **Settings in sections** (`Settings.svelte`): a section list beside the open section on a wide screen, centred and at a readable width; on a phone a list that opens each section with a way back. Sections are in the URL (`/settings/devices`). Profile, Playback, Appearance, Sign-in and security, Devices, API keys and About, plus an Administration link for admins (the server version lives on the admin dashboard now). Password and PIN forms open on demand; the password asks twice. Devices put this one first with rename in place, show relative times, call loopback addresses "on the server itself", and fold away sessions idle for over a week. A new `--on-accent` token gives text on accent fills its contrast in every theme (dark on Ember's orange).
- [x] **Playback preferences applied by the server**: default video quality, audio language, subtitle mode (off, signs and foreign dialogue, when the audio is in another language, always) and subtitle language, stored as preferences and applied when playback starts (`chooseAudio`, `chooseSubtitle`), so every client gets the same tracks. Language tags are folded to ISO 639-1 whatever spelling a file uses (`media.LanguageCode`: `fre`, `fra`, `'eng'`). Text subtitles are preferred over image ones; an image one is burned in from the start, except at "Original", which promises the untouched video. Turning a burned subtitle off in the player restarts without it and tells the server the viewer has chosen, so the preference is not reapplied.

- [x] **New episodes** (Plex's Recently Released Episodes): one card per episode that aired in the last six weeks, newest broadcast first, with the viewer's watched tick, on the TV library page and on Home (`GET /libraries/{id}/new-episodes`, `/home` `newEpisodes`). ## Storage
- [x] **A share that stops answering no longer hangs anything.** Resume once sat for over 30 minutes with nothing on screen: `media.Probe` blocked on a CIFS mount that had gone quiet, with no deadline, and every further press stacked another stuck request until the browser ran out of connections. Now a monitor checks each library's folders every 30 s (5 s per folder, never two stuck checks on one path); play and direct stream fail at once with 503 and a message naming the library, the folder and what to check when the storage is known to be down, and otherwise give the file 15 s before doing the same and re-checking the library. Scans fail fast; intro detection skips the library, gives each decode 3 minutes, leaves unreadable episodes to retry, and catches up when the storage returns. The web client says "Starting…" while a title starts, ignores repeat presses, shows any failure as a notice, and flags an unreachable library in the sidebar and on its pages; the admin's library table shows it too.
- [x] Storage that goes away during a transcode: a watchdog ends a session whose input has not advanced for 20 s while a client is waiting on it (a paused viewer or a throttled transcode is never judged); its playlist and segments then answer the storage 503 at once, and the library is re-checked. The player shows "Storage not responding" with the reason, saves the position, and offers Try again; a direct play that stops receiving data asks `GET /items/{id}/storage` why. A transcoder that exits with an error is reported at once instead of after 30 s.
- [x] Every read of media storage on a request path has a deadline (`library.OpenMedia`, `WithinIdle`): direct play, downloads and ZIPs, music transcodes, subtitle extraction, the probe, the folder picker. A path whose read was abandoned is refused until that read returns, so retries cannot pile more stuck reads onto a share. Direct play reads the share in 1 MiB chunks behind the deadline, so it costs a few guarded reads a second.
- [x] Seek-bar previews no longer compete with playback: they are built in the background (`internal/trickplay`) under the same rules as intro detection (`internal/background`: schedule, pause, read-speed cap, never while anything plays, scans or detects, stop when storage goes), queued after scans newest first and on first request, and kept in `libraries.previews_dir` rather than the transcode scratch, which is often RAM. Until they exist the seek bar shows none.
- [x] Previews of deleted items are removed from `previews_dir` at startup, after every completed scan and when a library is deleted. Only `<uuid>.jpg`/`.vtt` files directly in the folder whose item is gone are touched; other names, subfolders and media storage never are.
- [x] Rescans yield to playback: a scheduled sweep waits while anything plays (up to 2 hours), a Sonarr/Radarr webhook rescan up to 10 minutes; a scan started by hand runs at once.

## Milestone 6 — Admin UI
- [x] **Collection management**: a Collections tab on the library-management screen — rename, add/remove films, reorder, create one outright, or revert an edited one to the provider's grouping. Editing a provider collection *adopts* it (migration 0016): its membership and release order are copied into `collections`/`collection_items`, after which the managed rows are the truth, so a later scan cannot silently undo a manual change. The order set here is the order the collection plays in.
- [x] **Manual metadata editing**: an Edit dialog per film (title, year, certification, rating, tagline, synopsis, genres, poster/backdrop). Every field edited is *locked* (migration 0017) and `UpsertItem` skips locked columns, so scans and metadata refreshes leave corrections alone while still filling in everything untouched — without that, editing metadata is undone by the next refresh. An "edited" tag on the row clears the locks and hands the item back to the provider.
- [x] Multiple paths per library: the add form takes a list of rows, each with its own Browse… button, and rows can be added or removed.
- [x] Edit a library after creation (`PATCH /libraries/:id`): rename and change its paths. The media type stays immutable — everything already scanned keys off it, so changing it would orphan the lot; delete and recreate is the honest way. Removing a path does not delete its items directly; the next scan prunes whatever it no longer finds, keeping one rule for "the files went away".
- [x] Scan progress (files seen / total, progress bar, live via the event stream) and cancellation UI. Still open: current file name, files/sec.
- [x] `/fs/dirs` (folder picker) is registered on the admin-only group, so it no longer exposes directory names to a regular user.
- [x] **Dashboard stats persist, and plays record duration and completion.** Coarse samples (one a minute) are written to `stats_samples` and restored into the ring on startup, so the charts answer "was it struggling while I was out?" instead of starting blank — `stats.retention_hours` (default 24) sets how far back. The fine ring stays in memory and refills within the hour; passing minute-spaced rows off as fine samples would draw a chart whose shape lied. `play_events` gained `ended_at`, `secs` and `completed`, closed via a new `Registry.OnEnd` hook that fires on every exit path — explicit stop, transcode kill, and idle reap, because browsers close tabs without telling the server. Duration is wall-clock time the playback was open, not playhead movement, so seeking neither inflates nor deflates it. Surfaced on `GET /stats/plays/totals` (a new endpoint rather than a changed shape on `/stats/plays`) and in the Plays card as "4h 12m watched · 68% finished". Rows predating the columns read as zero seconds and not completed, which is what was measured for them.
- [x] **Direct-play entries can be stopped from the admin.** `DELETE /playbacks/{userId}/{itemId}` ends any playback, transcoding or not. A direct play has nothing to kill server-side — it is byte ranges over HTTP — so the client has to cooperate: the playback is dropped from the registry and marked stopped, and the next progress heartbeat is refused with 409, at which point the player pauses, releases the stream and tells the viewer why. The marker is needed because the heartbeat *re-registers* a playback it cannot find (so a reap or a restart does not lose a live stream), which would otherwise undo the stop seconds later. It is read once and expires after 90s: this ends a stream, it does not revoke access. The position sent with the refused beat is still saved, so resume lands where the viewer got to.
- [x] History retention: `libraries.history_retention_days` (default 90) prunes `audit_log` and `play_events`, swept alongside each scheduled rescan. 0 keeps everything. Both tables were append-only and growing without a ceiling or anyone watching.
- [x] Folder picker takes several folders at once: each row has a checkbox beside the name, and the footer button switches from "Select this folder" to "Add N folders". Extras become new path rows after the one that opened the picker, in the order ticked, with paths the library already holds dropped rather than duplicated. Verified at 1440px and 390px.

## Operational

- [x] `make build` echoed its own recipe, which put the TMDB key in the terminal, in scrollback and in any CI log that ever ran it. The key-bearing recipes are silenced with `@`. The key that was exposed this way should be rotated at themoviedb.org — silencing the recipe stops it happening again but does nothing about a key already seen.

- [x] **Firefox compatibility audited.** The one hard break was `Array.prototype.toSorted` in 7 places — an API, not syntax, so Vite's `firefox78` target neither transpiles nor flags it, and anything before Firefox 115 would have thrown and blanked the app. Replaced with `.filter(...).sort(...)`, which is safe at every site because each sorts a fresh array from a filter. Every remaining `-webkit-` property has its standard counterpart alongside (`background-clip`, `mask-image`, `::-moz-range-thumb` beside `::-webkit-slider-thumb`), and `-webkit-line-clamp` is supported by Firefox itself. The last `webkit` JS call (`webkitVideoDecodedByteCount`, used for a bitrate estimate) is gone.
- [x] Browser floor stated and built for: Chrome and Edge 111, Firefox 113, Safari and iOS 16.2, set by `color-mix()` (which degrades rather than breaks: an unsupported declaration is dropped and a tag loses its tint). The README says so, and both Vite configs set `build.target` and `cssTarget` to the same list, so esbuild lowers or prefixes what it can and fails the build on syntax those browsers cannot run. The two blur rules missing Safari's `-webkit-` prefix have it.
- [x] `docs/openapi.yaml` did not parse as YAML at all: an unquoted `{id}` inside a flow mapping (`description: Folder name; stylesheet at /themes/{id}/theme.css`) opened a nested flow collection. Since the spec is the contract third parties generate SDKs from, it was broken for every consumer. Now quoted and verified to parse (51 paths, 18 schemas).
- [x] The API spec is checked on every test run: `server/docs/docs_test.go` parses it and resolves every `$ref` and path parameter, and requires a unique operationId and one declared tag per operation; `internal/api/spec_test.go` compares it with the registered routes both ways. Its first run found 12 undocumented routes (library and item editing, collections, preferences, trickplay) and a stale subtitle path, now documented. The spec is also served at `/api/v1/openapi.yaml` and rendered with Swagger UI at `/api/docs`, which declares the session-cookie and API-key security schemes and groups operations by area.
- [x] CI (`.github/workflows/ci.yml`): every push and pull request builds the UIs, runs gofmt, go vet and the tests, and builds linux/amd64 and linux/arm64 binaries; a `v*` tag publishes them as a GitHub Release with `SHA256SUMS`. The static FFmpeg library is cached on the submodule commit and the patch's hash. `make build` now stamps the version (`git describe`, or the tag in CI).
- [x] golangci-lint (v2.14.0, `server/.golangci.yml`) runs in `make lint`, so CI gates on it. The first pass fixed 176 findings. Closes after a write are now checked (audio transcodes, HLS output, preview sheets, artwork downloads), as are re-enabling foreign keys after migrations and `.env` lines that cannot be set. Unused code is removed. Ignored: read-side closes (the standard preset), deferred `Tx.Rollback`, and errcheck in tests.
- [x] Release binaries need glibc 2.39+ (built on Ubuntu 24.04), which rules out Debian 12 and Ubuntu 22.04 for the plain binary. The container image settles it for everyone else: each `v*` tag also publishes a two-architecture Docker Hub image (Debian 13 base, with libva and the Mesa and Intel VA-API drivers) built from the release binaries, so the host's glibc no longer matters. A static musl build was ruled out: it cannot `dlopen` the host's libva, which would lose hardware transcoding.
- [ ] The container image is 555 MB, about 230 MB of it the Mesa VA-API driver and the LLVM it pulls in (what AMD hardware decode costs). Splitting a `-intel` and an `-amd` variant, or a software-only `-slim` tag, would shrink it for those who only need one.
- [ ] The image has not run end to end yet: a binary built locally on a rolling distribution needs a newer glibc than Debian 13 carries (2.44 here), so the first real test is a CI-built release. Tag a pre-release (`v0.2.0-rc.1`) to exercise the whole pipeline — binaries, GitHub Release and image — before the first real one.
- [x] Stale `running` scans marked failed at server startup; the scans table doubles as the cross-process scan lock.
- [x] **Response compression — done.** `middleware.GzipWithConfig` at level 5 with a 1 KiB floor. A library's item list went 1.1 MB → 303 KB and the client bundle 786 KB → 259 KB, both on the wire. Media, artwork and anything already compressed are skipped, and so is every range request: a range addresses the original bytes, so compressing the body afterwards would make `Content-Range` a lie and break seeking and resumable downloads. Covered by `TestIncompressible`.
- [x] `server/cineva.example.yaml` is now committed and carries all 17 config keys with their defaults and `CINEVA_*` env equivalents. `.gitignore` already promised this file existed; it never did, so the convention in CLAUDE.md was unfollowable.
